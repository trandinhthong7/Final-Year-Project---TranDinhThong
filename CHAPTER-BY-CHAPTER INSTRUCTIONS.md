CHAPTER-BY-CHAPTER INSTRUCTIONSChapter 1: IntroductionProblem Statement: Must include cited statistics or references proving the scale and significance of the problem.  Project Aim: Provide one comprehensive sentence stating what is being built, who it is for, and the benefit.  Specific Objectives:Must be strictly formatted using the SMART framework (Specific, Measurable, Achievable, Relevant, Time-bound).  Must contain quantifiable metrics (e.g., ">80% success rate", "<500ms latency").  Must reflect the full scope of the project lifecycle (e.g., research, design, testing, evaluation), not just the product build or coding tasks.  
Chapter 2: Background & Literature ReviewCompetitor Analysis (CRITICAL): When analyzing existing solutions, you MUST include a dedicated product review section comparing at least two similar products using Nielsen's 10 Usability Heuristics. Do not just list basic features.  Technology & Methodology Review: Provide a robust comparison of available methodological approaches and technologies. Support choices with research citations (e.g., why Agile is statistically better suited for this specific project than Waterfall).  Research Gap: Synthesize the findings into a clear, explicit "Research Gap" that the proposed project addresses.  
Chapter 3: Requirements AnalysisResearch Methodology: State exactly how data was/will be gathered (e.g., surveys, interviews) and who the participants are.  User Needs: Generate specific User Personas based on the research.  Functional Requirements: Format as User Stories ("As a [user], I want [action] so that [benefit]") and prioritize them strictly using the MoSCoW method (Must, Should, Could, Won't).  
Chapter 4: Methodology & Project PlanningMethodology Application: Detail exactly how the chosen methodology (e.g., Agile Scrum) is applied in practice (e.g., sprint lengths, daily standups).  Gantt Chart / Timeline (CRITICAL): The project plan MUST reflect true Agile planning. It must clearly illustrate parallel/concurrent front-end and back-end activities, logical interdependencies, and iterative testing. Do NOT generate a linear, cascading "Waterfall" timeline.  Success Metrics: Define both quantitative (e.g., API response time, SUS scores) and qualitative metrics for evaluating the project.  
Chapter 5: System Design & ArchitectureVisual Documentation: Provide textual descriptions formatted to easily convert into architectural diagrams, such as:Rich Picture: Visualizing the whole system context.  C4 Model: Context and Container level diagrams.  Entity Relationship Diagram (ERD): Database blueprint.  API Design: Include a structured table of key API endpoints (Method, URL, Auth, Description).  
Chapter 6: Implementation (CRITICAL GUARDRAILS)NO CODE DUMPS: Absolutely forbid pasting long walls of code (maximum 15-20 lines per snippet).  NO EXCESSIVE SCREENSHOTS: Limit UI screen dumps. Focus the text on critical evaluation.  Focus on 'Why', not 'What': Do not explain basic syntax. Extract only complex architectural decisions, security implementations, or novel algorithms. Critically evaluate why the code was structured this way and justify the development decisions using research.  
Chapter 7: TestingMulti-layered Strategy: Detail a testing strategy that includes Unit Testing, Integration Testing, and User Acceptance Testing (UAT).  Test Cases: Present a structured table of test cases (ID, Description, Steps, Expected Result, Actual Result, Pass/Fail).  UAT Results: Evaluate the UAT against the specific quantitative metrics defined in Chapter 4 (e.g., Task Completion Rate, System Usability Scale score).  
Chapter 8: Legal, Social, Ethical, and Professional Issues (LSEPI)Deep Paragraphs, No Tables: Write substantial paragraphs for each LSEPI category. Do not use superficial bullet points or basic tables.  Citation Mandate: Every issue discussed must be supported by relevant academic citations, legal frameworks (e.g., GDPR for data privacy), or professional guidelines (e.g., BCS Code of Conduct).  
Chapter 9: Conclusion & Critical ReflectionEvaluate Against Objectives: Explicitly restate the SMART objectives defined in Chapter 1 and evaluate whether each was achieved using evidence.  Critical Evaluation: Honestly discuss what went well and what failed (e.g., integration delays, scope changes) and how challenges were mitigated.  Future Work: Provide a realistic roadmap for technical improvements and feature additions.
